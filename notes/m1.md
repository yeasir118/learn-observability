## TS-026: React frontend app

**1. What's in `dist/` after a build, and why do asset names contain a hash?**
`index.html`, `favicon.svg` (copied as is from `public/`), and one JavaScript and one CSS file under `assets/`, e.g. `index-Ba3rw7DJ.js`. The hash is computed from the file's content: it changes exactly when the content changes. So a name identifies one exact version of a file, and a browser can cache it forever; a new build produces new names. `index.html` is the one file whose name never changes and which points at the current names, so it must never be cached (TS-015, decision 6).

**2. Dev and built app call the same `/api/...` URLs. Who answers them?**
Always the origin the page came from, so the browser never knows what's behind it, and there's no CORS:
- `npm run dev` / `npm run preview`: Vite's server, which proxies to `GATEWAY_URL` (default `localhost:5100`). With nothing there, Vite answers its own empty `text/plain` 502.
- In the container (TS-015): nginx, which proxies to `gateway:8080`.

## TS-015: Frontend container and nginx reverse proxy

**1. `proxy_pass http://gateway:8080;` versus `proxy_pass http://gateway:8080/;`: what path reaches the gateway for `/api/orders/1001`?**
Without a URI part (no `/` after the port), nginx passes the request URI unchanged: `/api/orders/1001`, query included. With one, nginx replaces the part the `location` matched (`/api/`) with that URI (`/`): `/orders/1001`. Shown in Phase 0, and with the echo server: `GET /api/orders/1001?x=1` arrived exactly as sent. The gateway owns `/api/*` (TS-014, Q5), so ours has no URI part. A variable (`proxy_pass $gateway;`) with no URI part also passes the request URI as is.

**2. The gateway is recreated while nginx keeps running. Literal `proxy_pass` versus `resolver` plus a variable?**
- Literal name: resolved once, when nginx starts. A recreated gateway can get a new IP; nginx keeps connecting to the old one and answers 502 until it's restarted. And if `gateway` doesn't exist at startup, nginx doesn't start at all (`[emerg] host not found in upstream "gateway"`, Phase 0).
- Variable plus `resolver 127.0.0.11 valid=10s`: resolved per request, the answer cached for 10 s. Measured: the gateway went from `.3` to `.4` (another container took `.3`). The next requests were 502, 502 (the cached `.3`, now refusing), then 200 to `.4`, with no restart. Docker's DNS gives a TTL of 600 s, so without `valid=` that would have been up to 10 minutes of 502s.

**3. order-service hangs for 120 s on `POST /api/orders`. What does the browser get, from which component, after how long? What happens to the order?**
Measured with `docker pause order-service` for 120 s: the browser got **504 `upstream_timeout` from nginx after ~60 s** (`proxy_read_timeout`; no `traceId`, so not .NET). The gateway's 100 s never came into play: it sends its call with the request's `RequestAborted`, so when nginx closed its connection, the gateway dropped its call to order-service too. The frozen order-service then found the connection closed and never ran the request: **no order**.
That's the "hung before reading" case. A service that hangs *after* inserting the order (e.g. waiting for payment, whose gRPC call has no deadline) keeps going: the order exists as `PENDING` and may still become `PAID`, while the browser was told 504. A retry then creates a second order: the browser can't tell the two cases apart (contracts.md §7, §8).

**4. Why could your phone reach the app? What would `127.0.0.1:8000:8080` change?**
`"8000:8080"` publishes on every host interface (`0.0.0.0` and `[::]`), including the Wi-Fi/LAN one, so a device on the same network can connect to `http://<PC's LAN IP>:8000`, as long as Windows Firewall allows inbound connections to Docker Desktop's port forwarder. `127.0.0.1:8000:8080` would bind only the loopback interface: the app works on this PC, and nothing else can reach it, like the debug proxies.
nginx doesn't see the phone's address in either case: `$remote_addr` (and so `X-Forwarded-For`) is the Docker network's bridge gateway (`172.x.0.1`), because the published port reaches the container through Docker's NAT.

**5. Why must `index.html` not be cached, when `/assets/*.js` can be cached for a year?**
An asset's name contains a hash of its content, so a new build produces new names: a cached `index-Ba3rw7DJ.js` is never wrong, it's just no longer referenced. `index.html` has a fixed name and is the file that says which hashed names to load. Cached, a browser would keep loading the old app after a deploy. `no-cache` doesn't mean "don't store": the browser stores it but asks every time, and nginx answers `304 Not Modified` (via `ETag`) when nothing changed, a round trip without a body. In DevTools: the JS comes from the memory/disk cache, the document is a 304.

**6. Who can be trusted to set `X-Forwarded-For`? What would `$proxy_add_x_forwarded_for` forward if a browser sent its own value?**
Only a proxy you control, and only for the hop it saw itself: the first one, here nginx, which knows the address that opened the TCP connection (`$remote_addr`). Anything the client sends is a claim. `$proxy_add_x_forwarded_for` appends `$remote_addr` to the client's header, so a browser sending `X-Forwarded-For: 6.6.6.6` would arrive as `6.6.6.6, 172.x.0.1`, and code that takes the first entry would believe the lie. With `$remote_addr` alone, the echo server received `172.20.0.1`, never `6.6.6.6`. Proxies behind nginx (the gateway) append or pass through; they don't overwrite.

**7. Which HTTP version and `Connection` header does nginx use towards the gateway? What does the gateway do with it?**
HTTP/1.1, and no `Connection` header at all (nginx 1.30; older versions sent HTTP/1.0 with `Connection: close`, which is why many guides still add `proxy_http_version 1.1`). The client's own `Connection: keep-alive` isn't forwarded: it's hop-by-hop, it describes the browser↔nginx connection only. The gateway applies the same rule on its side (TS-014): it drops hop-by-hop headers before forwarding to a service.
