## TS-026: React frontend app

**1. What's in `dist/` after a build, and why do asset names contain a hash?**
`index.html`, `favicon.svg` (copied as is from `public/`), and one JavaScript and one CSS file under `assets/`, e.g. `index-Ba3rw7DJ.js`. The hash is computed from the file's content: it changes exactly when the content changes. So a name identifies one exact version of a file, and a browser can cache it forever; a new build produces new names. `index.html` is the one file whose name never changes and which points at the current names, so it must never be cached (TS-015, decision 6).

**2. Dev and built app call the same `/api/...` URLs. Who answers them?**
Always the origin the page came from, so the browser never knows what's behind it, and there's no CORS:
- `npm run dev` / `npm run preview`: Vite's server, which proxies to `GATEWAY_URL` (default `localhost:5100`). With nothing there, Vite answers its own empty `text/plain` 502.
- In the container (TS-015): nginx, which proxies to `gateway:8080`.

## TS-015: Frontend container and nginx reverse proxy

**1. `proxy_pass http://gateway:8080;` versus `proxy_pass http://gateway:8080/;`: what path reaches the gateway for `/api/orders/1001`?**
Without a URI part (no `/` after the port), nginx passes the request URI unchanged: `/api/orders/1001`, query included. With one, nginx replaces the part the `location` matched (`/api/`) with that URI (`/`): `/orders/1001`. Shown in Phase 0, and with the echo server: `GET /api/orders/1001?x=1` arrived exactly as sent. The gateway owns `/api/*` (TS-014, Q5), so ours has no URI part. A variable (`proxy_pass $gateway;`) with no URI part also passes the request URI as is.

**2. The gateway is recreated while nginx keeps running. Literal `proxy_pass` versus `resolver` plus a variable?**
- Literal name: resolved once, when nginx starts. A recreated gateway can get a new IP; nginx keeps connecting to the old one and answers 502 until it's restarted. And if `gateway` doesn't exist at startup, nginx doesn't start at all (`[emerg] host not found in upstream "gateway"`, Phase 0).
- Variable plus `resolver 127.0.0.11 valid=10s`: resolved per request, the answer cached for 10 s. Measured: the gateway went from `.3` to `.4` (another container took `.3`). The next requests were 502, 502 (the cached `.3`, now refusing), then 200 to `.4`, with no restart. Docker's DNS gives a TTL of 600 s, so without `valid=` that would have been up to 10 minutes of 502s.

**3. order-service hangs for 120 s on `POST /api/orders`. What does the browser get, from which component, after how long? What happens to the order?**
Measured with `docker pause order-service` for 120 s: the browser got **504 `upstream_timeout` from nginx after ~60 s** (`proxy_read_timeout`; no `traceId`, so not .NET). The gateway's 100 s never came into play: it sends its call with the request's `RequestAborted`, so when nginx closed its connection, the gateway dropped its call to order-service too. The frozen order-service then found the connection closed and never ran the request: **no order**.
That's the "hung before reading" case. A service that hangs *after* inserting the order (e.g. waiting for payment, whose gRPC call has no deadline) keeps going: the order exists as `PENDING` and may still become `PAID`, while the browser was told 504. A retry then creates a second order: the browser can't tell the two cases apart (contracts.md §7, §8).

**4. Why could your phone reach the app? What would `127.0.0.1:8000:8080` change?**
`"8000:8080"` publishes on every host interface (`0.0.0.0` and `[::]`), including the Wi-Fi/LAN one, so a device on the same network can connect to `http://<PC's LAN IP>:8000`, as long as Windows Firewall allows inbound connections to Docker Desktop's port forwarder. `127.0.0.1:8000:8080` would bind only the loopback interface: the app works on this PC, and nothing else can reach it, like the debug proxies.
nginx doesn't see the phone's address in either case: `$remote_addr` (and so `X-Forwarded-For`) is the Docker network's bridge gateway (`172.x.0.1`), because the published port reaches the container through Docker's NAT.

**5. Why must `index.html` not be cached, when `/assets/*.js` can be cached for a year?**
An asset's name contains a hash of its content, so a new build produces new names: a cached `index-Ba3rw7DJ.js` is never wrong, it's just no longer referenced. `index.html` has a fixed name and is the file that says which hashed names to load. Cached, a browser would keep loading the old app after a deploy. `no-cache` doesn't mean "don't store": the browser stores it but asks every time, and nginx answers `304 Not Modified` (via `ETag`) when nothing changed, a round trip without a body. In DevTools: the JS comes from the memory/disk cache, the document is a 304.

**6. Who can be trusted to set `X-Forwarded-For`? What would `$proxy_add_x_forwarded_for` forward if a browser sent its own value?**
Only a proxy you control, and only for the hop it saw itself: the first one, here nginx, which knows the address that opened the TCP connection (`$remote_addr`). Anything the client sends is a claim. `$proxy_add_x_forwarded_for` appends `$remote_addr` to the client's header, so a browser sending `X-Forwarded-For: 6.6.6.6` would arrive as `6.6.6.6, 172.x.0.1`, and code that takes the first entry would believe the lie. With `$remote_addr` alone, the echo server received `172.20.0.1`, never `6.6.6.6`. Proxies behind nginx (the gateway) append or pass through; they don't overwrite.

**7. Which HTTP version and `Connection` header does nginx use towards the gateway? What does the gateway do with it?**
HTTP/1.1, and no `Connection` header at all (nginx 1.30; older versions sent HTTP/1.0 with `Connection: close`, which is why many guides still add `proxy_http_version 1.1`). The client's own `Connection: keep-alive` isn't forwarded: it's hop-by-hop, it describes the browser↔nginx connection only. The gateway applies the same rule on its side (TS-014): it drops hop-by-hop headers before forwarding to a service.

## TS-016: Fault injection switches

**1. Why `pg_sleep` inside the command rather than `Task.Delay` around it? What would each look like in a trace?**
A trace shows where time was spent by span. With `pg_sleep` the wait happens in Postgres, inside the command, so the **database span** of that query gets long: "the database operation is slow". With `Task.Delay` in C# the database span stays short, and the time shows up in the service's own span with no child to explain it: "the application code is slow". That's the wrong lesson for Exercise 3, which asks exactly "is the network call slow, or the database operation?". It would also be invisible to the database's own tools (`pg_stat_activity`, slow-query logs), where a real slow query shows up.
The wait is **appended** to the command: a statement in front shifts EF Core's per-statement results, and an UPDATE then looks like it changed 0 rows (`DbUpdateConcurrencyException`). And only the application's commands are delayed: the readiness check's `SELECT 1` goes through EF Core too.

**2. What does the browser see for a declined payment, and for a technical payment error? Why is one a 201 and the other a 502?**
- Decline: **201**, the order with `status: FAILED`, `failureReason: card_declined`.
- Technical error: **502 `payment_unavailable`**, with `orderId` (the order is `FAILED` too).

A decline is a business outcome: every system worked, and the card was refused. The request to create an order succeeded, and the order records the result. A technical error means a system failed (payment-service threw, gRPC `INTERNAL`), so order-service couldn't do its job: a 5xx, and 502 because it was a dependency that failed, not order-service itself. Clients branch differently: show "card declined", or "try again later".

**3. Why must the health endpoints never be affected by a fault?**
Health checks answer "is this container able to work?" for Docker. A 20 % error fault on `/health/ready` would mark the container unhealthy, fail `docker compose up --wait` and the CI `network` job, and in an orchestrator get it restarted or removed from the load balancer. The exercise would then be about restarts instead of the fault. It's the same reason the gateway's readiness checks nothing upstream (TS-014): a fault elsewhere must not cascade into "unhealthy". The database-delay fault taught it the hard way: the readiness check goes through EF Core, so it had to be excluded explicitly.

**4. product-service fails 20 % of its requests. What share of orders fails, and why?**
About **20 %**. An order makes exactly **one** call to product-service (`GET /products/{id}`), and nothing retries, so each order has one 20 % chance to fail with 502 `dependency_failed`. The share grows with the number of calls: with n calls each failing independently at 20 %, 1 − 0.8ⁿ fail (two calls: 36 %). A retry would lower it (two tries: 0.2² = 4 %), but only for a request that's safe to repeat (D5: no retries in M1). The shop page's product list fails at 20 % too.

**5. Why is a fault that throws an exception more realistic than one that returns a 500?**
A real 500 is almost always an unhandled exception, and it leaves evidence: an error log line with the exception type, message and stack trace, and the request path. That's what Exercise 1 investigates. A `return StatusCode(500)` produces the same response but no log entry at all, so nothing could be found from the server side. Thrown, it also takes the real error path (the exception handler, Problem Details `internal_error` with a `traceId`, in payment-service the gRPC interceptor and `INTERNAL`), so the exercises test the plumbing that real failures use.

**Also learned in the experiments:**
- A 60 s payment delay leaves the order `PENDING` for good. nginx gives up at 60 s, and the cancellation travels the whole chain: gateway, order-service, payment-service ("cancelled by the caller"). order-service treats a cancelled call as "my caller left", so nothing ever updates the order (contracts.md §7, §8).
- `docker compose up -d` starts the exited migration jobs again: harmless, migrations are idempotent.

## TS-017: Load generator (k6)

**1. Open against closed model: with `PAYMENT_SERVICE_FAULT_DELAY=00:00:03`, what happens to the number of orders per second in each, and why?**
- **Open** (`constant-arrival-rate`, what we use): orders per second **stays the same**. New iterations start on schedule whether earlier ones have finished or not, so more are in flight at once: 2 orders/s × 3 s = about 6 waiting at any moment (more VUs needed; too few and k6 reports `dropped_iterations`).
- **Closed** (a fixed number of VUs, each waiting for its answer before the next request): orders per second **drops**. 10 VUs that each need 3 s manage about 3 orders/s instead of many more.

Real users keep arriving whether the shop is slow or not. In the closed model the system's slowness lowers its own load, so the test hides the very problem it should show (*coordinated omission*).

**2. Why is a 422 in the invalid journey not a failure, while a 502 is?**
A failure is an **unexpected** answer, not simply a 4xx or 5xx. Refusing an order for an unknown user with 422 is the system working correctly: we asked for something invalid, and it said so. A 502 means the system couldn't do its job (a dependency failed), whatever the input. The same 422 in the *valid* order journey would be a failure, which is why `http.expectedStatuses(422)` is set on the invalid request only.

**3. What does p95 tell you that the average doesn't?**
p95 is the time that 95 % of requests finished within: the slowest 5 % took longer. That tail is what unlucky users feel. The average (sum ÷ count; the *middle* is the median) is pulled up by a few very slow requests and blends different groups into one number that describes none of them. Example from TS-017: `POST /api/orders` had a minimum of 6 ms but a median of 65 ms, because invalid orders are refused at once while real ones wait for the payment.

**4. With a payment delay on, what can the k6 report tell you, and what can't it? What would you need to find which service is slow?**
- **It can tell** what the user experienced: which route got slower (`POST /api/orders` by about 3 s, the others unchanged), by how much (percentiles), whether anything failed, and when it started.
- **It can't tell** where the time went: nginx, the gateway, order-service, the database or payment-service all look the same from outside.
- **To find it:** a view from inside. A **trace** shows one span per hop with its duration (the gRPC call to payment-service would be the long one); per-service **metrics** show which service's latency rose; **logs** with timings help too. That's M2 and M3.

**5. Why group requests by route (`GET /api/orders/{id}`) instead of the real URL?**
Every order has its own URL. Without a route name, each one becomes its own row in the summary and the report, with a single sample: the number of rows grows without limit and none of them says anything. Grouped, all reads of an order form one row with meaningful counts and percentiles. That's the cardinality problem, which returns with metric labels in M3: never use an ID as a label.

**Also learned:**
- `docker compose down` without `--profile load` leaves the stopped `load-generator` container behind but removes the project's networks. The next `up` starts that old container, which still points at the old network's ID: "network … not found". Use `docker compose --profile load down`, and `run --rm` for the test container.
- `docker compose up load-generator` shows the logs of every dependency too. `docker compose --profile load run --rm --service-ports load-generator` shows only k6's output (`--service-ports`, because `run` doesn't publish ports by default) and returns k6's exit code.

## Known gaps of M1

Left open on purpose (epic TS-001; the full list with the usual fixes is in contracts.md §8). Later milestones make them visible first, then fix them.

- **Duplicate orders on retry.** `POST /api/orders` has no idempotency key. When a client gets no answer (a timeout, a dropped connection) it can't tell "no order was created" from "the order exists, the answer was lost", and a retry creates a second order and a second payment. Seen in TS-015: a hang before the order is inserted leaves no order; a hang after it leaves one.
- **Orders stuck in `PENDING`.** The order is inserted as `PENDING` before payment. If the payment's outcome never arrives (the caller gave up and the cancellation stopped the call, or the status update after a successful payment failed), nothing ever resolves it: no reconciliation job. Measured in TS-016: a 60 s payment delay leaves the order `PENDING` for good.
- **No timeouts and no retries of our own** (decision D5). Only library defaults apply, and they don't fit together: nginx gives up after 60 s, the HTTP clients after 100 s, the gRPC call to payment-service **never** (contracts.md §7). Nothing is retried, so every transient failure reaches the user (TS-016: 20 % failing product calls mean 20 % failing orders).
