# TinyShop API contracts

This document is the source of truth for every HTTP interface in TinyShop. Services are built to match it; if the code and this document disagree, the code is wrong or this document must be changed first.

- Containers, ports and networks: [architecture.md](architecture.md)
- gRPC contract for the Payment service: [§9](#9-payment-grpc-contract) (TS-005)

## 1. Conventions

These apply to every endpoint unless the endpoint says otherwise.

| Topic | Convention | Why |
|---|---|---|
| Format | Request and response bodies are JSON (`application/json; charset=utf-8`). Errors use `application/problem+json`. | Standard for HTTP APIs |
| Field names | `camelCase` | Default in System.Text.Json's web settings and natural for JavaScript clients, so neither side needs a renaming layer |
| Enum values | `UPPER_SNAKE_CASE` strings, never numbers (`"PAID"`) | Readable in logs and stable if the enum's order changes in code |
| IDs | Positive 64-bit integers (`bigint` identity columns in Postgres, `long` in C#, JSON number) | See [§1.1](#11-ids) |
| Money | Integer **minor units** (cents) in a field whose name ends in `Cents`. All amounts are USD. | See [§1.2](#12-money) |
| Timestamps | RFC 3339 strings in UTC with a `Z` suffix and millisecond precision: `"2026-10-18T14:30:05.123Z"` | See [§1.3](#13-timestamps) |
| Null | Optional fields are always present, with value `null` when empty. They are never omitted. | One shape per resource; clients never test for "missing" and "null" separately |
| Unknown request fields | Ignored | Lets clients and servers evolve independently |
| Collections | Wrapped in an object: `{ "items": [ ... ] }`, never a bare array | Pagination or metadata can be added later without breaking clients |
| Versioning, authentication, pagination | Out of scope for M1 | |

### 1.1 IDs

IDs are sequential integers generated by Postgres (`GENERATED ALWAYS AS IDENTITY`).

- **Why integers:** users type IDs into the UI (`User ID: 123`), and integers are short and readable in logs while investigating.
- **Trade-off:** sequential IDs reveal how many records exist and are easy to enumerate (`/orders/1`, `/orders/2`, …). Public APIs in production usually expose random or time-ordered UUIDs (for example UUIDv7) instead. That doesn't matter for a lab without authentication.
- 64-bit, so they never run out. JavaScript can represent integers exactly up to 2⁵³, far beyond anything TinyShop will reach.

### 1.2 Money

Every amount is an integer number of cents, from the database to the browser:

| Layer | Type |
|---|---|
| Postgres | `bigint` |
| C# | `long` |
| JSON | integer (`"priceCents": 10000` means $100.00) |
| Protobuf | `int64` (see [§9](#9-payment-grpc-contract)) |

- **Why not floating point:** binary floating point can't represent most decimal fractions exactly (`0.1 + 0.2 != 0.3`), so totals drift by fractions of a cent.
- **Why integers rather than decimals:** C# `decimal` and Postgres `numeric` are exact, but JSON has no decimal type: JavaScript parses every JSON number as a double, and protobuf has no decimal type at all. Integer cents is the one representation that stays exact in every layer with no conversion. Stripe and Adyen use the same approach.
- **The `Cents` suffix is required** so nobody mistakes `10000` for $10,000.
- **Formatting is the client's job:** the frontend divides by 100 for display only. All arithmetic (`total = price × quantity`) happens on the server.

### 1.3 Timestamps

- Stored as Postgres `timestamptz`, handled in C# as `DateTimeOffset` or a UTC `DateTime`.
- Always UTC on the wire. Converting to local time is a display concern for the client.
- Implementation note: Npgsql refuses to write a `DateTime` whose `Kind` isn't `Utc` to a `timestamptz` column. Use `DateTimeOffset.UtcNow` or `DateTime.UtcNow`.

## 2. Errors

### 2.1 Problem Details

Every error response is an RFC 9457 Problem Details object with an extra `code` field:

```http
HTTP/1.1 422 Unprocessable Content
Content-Type: application/problem+json

{
  "type": "https://tinyshop.example/problems/user_not_found",
  "title": "User not found",
  "status": 422,
  "detail": "User 999 does not exist.",
  "instance": "/api/orders",
  "code": "user_not_found",
  "traceId": "00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01"
}
```

| Field | Meaning |
|---|---|
| `type` | URI identifying the problem type. Derived from `code`; it doesn't have to resolve to a web page. |
| `title` | Short, human-readable summary of the problem type. The same for every occurrence of a `code`. |
| `status` | The HTTP status code, repeated in the body |
| `detail` | Human-readable explanation of this occurrence. Never contains stack traces, hostnames or internal service names. |
| `instance` | The request path |
| `code` | **Stable, machine-readable `snake_case` identifier. Clients branch on this field and nothing else.** |
| `traceId` | Added automatically by ASP.NET Core. Its meaning is explored in later phases. |

Error-specific extension fields:

- **Validation errors** add `errors`: a map from field name (`camelCase`) to a list of messages.
- **Order errors raised after the order row exists** add `orderId`, so the client can look the order up.

Implementation note: errors that the framework generates itself (malformed JSON, wrong content type, unmatched routes) must also carry a `code`. Configure this once in `AddProblemDetails(options => options.CustomizeProblemDetails = ...)`.

### 2.2 Status code rules

| Status | Meaning in TinyShop |
|---|---|
| 400 | The request is malformed: invalid JSON, missing fields, wrong types, values out of range |
| 404 | The resource named in the URL doesn't exist |
| 415 | The request body isn't `application/json` |
| 422 | The request is well-formed but refers to something that doesn't exist (an unknown user or product in `POST /orders`) |
| 500 | I broke: a bug or unhandled exception in this service |
| 502 | Something I depend on failed: it returned a 5xx or an unexpected response, or I couldn't connect to it |
| 503 | I can't serve right now: my own database is unreachable |
| 504 | Something I depend on didn't answer in time |

**Rule of thumb:** if the client retried the exact same request later, could it succeed? If yes, it's a 5xx. If no, it's a 4xx.

### 2.3 Error code catalog

| `code` | Status | Raised by | Meaning |
|---|---|---|---|
| `validation_failed` | 400 | any service | Body, path or query parameter is malformed. See `errors`. |
| `unsupported_media_type` | 415 | any service | Request body isn't JSON |
| `user_not_found` | 404 or 422 | user-service (404), order-service (422) | No user with that ID |
| `product_not_found` | 404 or 422 | product-service (404), order-service (422) | No product with that ID |
| `order_not_found` | 404 | order-service | No order with that ID |
| `dependency_failed` | 502 | order-service | A service it depends on failed or couldn't be reached |
| `dependency_timeout` | 504 | order-service | A service it depends on timed out |
| `payment_unavailable` | 502 | order-service | The order was created, but the payment service failed or couldn't be reached. The order is `FAILED`; includes `orderId`. |
| `payment_timeout` | 504 | order-service | The order was created, but the payment call timed out. The outcome is unknown and the order stays `PENDING`; includes `orderId`. |
| `service_unavailable` | 503 | any service with a database | The service's own database is unreachable |
| `upstream_unreachable` | 502 | gateway | The gateway couldn't connect to the internal service |
| `upstream_timeout` | 504 | gateway | The internal service didn't answer in time |
| `internal_error` | 500 | any service | An unexpected error in the service itself |

`user_not_found` and `product_not_found` keep the same `code` with different statuses: the code says what the problem is, and the status says how it relates to the URL that was called.

The `upstream_*` codes come only from the gateway, and the `dependency_*` codes only from services behind it. So a client can tell whether the failure happened at the gateway or deeper in the system, but not which internal service failed. That's intentional (see Failure Exercise 1).

### 2.4 How errors pass between services

1. **The gateway passes responses through unchanged.** It forwards the status, headers and body exactly as the internal service sent them, with one exception: the `Location` header (rule 3). The gateway only creates its own errors when it can't get a response at all (`upstream_unreachable`, `upstream_timeout`) or when it fails itself (`internal_error`).
2. **Services translate errors and never pass them through.** A dependency's status code describes the dependency's resource, not yours. The order-service's full translation is in [§6](#6-order-service-dependency-failure-translation).
3. **The gateway rewrites `Location`** from an internal path to the public path: `/orders/1001` becomes `/api/orders/1001`.
4. **The service that owns the data validates requests.** The gateway doesn't validate request bodies.

### Product

```json
{
  "id": 1,
  "name": "Keyboard",
  "priceCents": 10000
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | integer | |
| `name` | string | 1–100 characters |
| `priceCents` | integer | > 0 |

### User
```json
{
  "id": 123,
  "name": "Alice"
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | integer | |
| `name` | string | 1–100 characters |

### Order
```json
{
  "id": 1001,
  "userId": 123,
  "productId": 1,
  "productName": "Keyboard",
  "unitPriceCents": 10000,
  "quantity": 2,
  "totalCents": 20000,
  "status": "PAID",
  "failureReason": null,
  "transactionId": "txn_8f14e45f",
  "createdAt": "2026-10-18T14:30:05.123Z",
  "updatedAt": "2026-10-18T14:30:05.187Z"
}
```

| Field | Type | Notes |
|---|---|---|
| `id` | integer | |
| `userId` | integer | |
| `productId` | integer | |
| `productName` | string | Snapshot of the product name when the order was created |
| `unitPriceCents` | integer | Snapshot of the product price when the order was created |
| `quantity` | integer | 1–100 |
| `totalCents` | integer | `unitPriceCents × quantity`, computed by order-service |
| `status` | string | `PENDING`, `PAID` or `FAILED` |
| `failureReason` | string or null | Set only when `status` is `FAILED`. Either the payment service's decline reason, or `payment_unavailable` for a technical failure. |
| `transactionId` | string or null | Set only when `status` is `PAID`. Opaque string from the payment service. |
| `createdAt` | timestamp | |
| `updatedAt` | timestamp | Changes when the status changes |

The product name and price are copied into the order deliberately. An order records what the customer bought at the price they paid; a later price change in product-service must not change existing orders. This also means reading an order needs no calls to other services.

## 4. Public API (gateway)

The browser calls these, through nginx at `http://localhost:8000`. Each public route forwards to exactly one internal route:

| Public route | Forwards to |
|---|---|
| `GET /api/products` | product-service `GET /products` |
| `GET /api/users/{id}` | user-service `GET /users/{id}` |
| `POST /api/orders` | order-service `POST /orders` |
| `GET /api/orders/{id}` | order-service `GET /orders/{id}` |
| `GET /api/orders?userId={id}` | order-service `GET /orders?userId={id}` |

Internal endpoints that aren't in this table (for example `GET /products/{id}`, and the health endpoints) aren't reachable from the browser.

Because the gateway passes responses through ([§2.4](#24-how-errors-pass-between-services)), each public endpoint returns:

- every response of the internal endpoint it forwards to (documented in [§5](#5-internal-apis)), plus
- the gateway's own errors:

| Status | `code` | When |
|---|---|---|
| 502 | `upstream_unreachable` | The gateway couldn't connect to the internal service (connection refused, DNS failure) |
| 504 | `upstream_timeout` | The internal service didn't answer within the gateway's timeout |
| 500 | `internal_error` | Bug in the gateway itself |

### Example: `POST /api/orders`

```http
POST /api/orders HTTP/1.1
Host: localhost:8000
Content-Type: application/json

{ "userId": 123, "productId": 1, "quantity": 2 }
```

```http
HTTP/1.1 201 Created
Location: /api/orders/1001
Content-Type: application/json; charset=utf-8

{ "id": 1001, "userId": 123, "productId": 1, "productName": "Keyboard", "unitPriceCents": 10000,
  "quantity": 2, "totalCents": 20000, "status": "PAID", "failureReason": null,
  "transactionId": "txn_8f14e45f", "createdAt": "2026-10-18T14:30:05.123Z", "updatedAt": "2026-10-18T14:30:05.187Z" }
```

## 5. Internal APIs

These are called only inside Docker (base URL `http://<service>:8080`).

### 5.1 product-service

#### `GET /products`
List all products, ordered by `id`.

- **200 OK:**
  ```json
  { "items": [ { "id": 1, "name": "Laptop", "priceCents": 100000 }, { "id": 2, "name": "Keyboard", "priceCents": 10000 } ] }
  ```
  An empty catalogue returns `{ "items": [] }`.
- **Errors:**

  | Status | `code` | When |
  |---|---|---|
  | 503 | `service_unavailable` | product-db unreachable |
  | 500 | `internal_error` | unexpected error |

#### `GET /products/{id}`
Get one product. Used by order-service only.

- **200 OK:** a Product.
- **Errors:**

  | Status | `code` | When |
  |---|---|---|
  | 400 | `validation_failed` | `id` isn't an integer |
  | 404 | `product_not_found` | No product with that ID (including 0 or negative IDs) |
  | 503 | `service_unavailable` | product-db unreachable |
  | 500 | `internal_error` | unexpected error |

### 5.2 user-service

#### `GET /users/{id}`
Get one user. Called by the gateway (the UI's user lookup) and by order-service (validating the user).

- **200 OK:** a User.
- **Errors:**

  | Status | `code` | When |
  |---|---|---|
  | 400 | `validation_failed` | `id` isn't an integer |
  | 404 | `user_not_found` | No user with that ID |
  | 503 | `service_unavailable` | user-db unreachable |
  | 500 | `internal_error` | unexpected error |

### 5.3 order-service

#### `POST /orders`
Create an order and attempt payment. The flow is shown step by step in [architecture.md §6](architecture.md#6-request-flow-post-apiorders).

- **Request body:**

  | Field | Type | Required | Rules |
  |---|---|---|---|
  | `userId` | integer | yes | > 0 |
  | `productId` | integer | yes | > 0 |
  | `quantity` | integer | yes | 1–100 |

  ```json
  { "userId": 123, "productId": 1, "quantity": 2 }
  ```

- **201 Created:** `Location: /orders/{id}`, and the Order in the body. **Returned whether the payment was approved (`status: PAID`) or declined (`status: FAILED`).** A decline is a business outcome, not an error (provisional; revisited in Exercise 4).

- **Errors:**

  | Status | `code` | When | Order |
  |---|---|---|---|
  | 400 | `validation_failed` | Malformed JSON, missing field, wrong type, value out of range | not created |
  | 415 | `unsupported_media_type` | Body isn't JSON | not created |
  | 422 | `user_not_found` | user-service returned 404 | not created |
  | 422 | `product_not_found` | product-service returned 404 | not created |
  | 502 | `dependency_failed` | user-service or product-service failed or couldn't be reached | not created |
  | 504 | `dependency_timeout` | user-service or product-service timed out | not created |
  | 502 | `payment_unavailable` | payment-service failed or couldn't be reached | `FAILED` |
  | 504 | `payment_timeout` | the payment call timed out | stays `PENDING` |
  | 503 | `service_unavailable` | order-db unreachable | not created, or see [§8](#8-known-gaps) |
  | 500 | `internal_error` | unexpected error | depends on where it failed |

  Validation error example:

  ```json
  {
    "type": "https://tinyshop.example/problems/validation_failed",
    "title": "Validation failed",
    "status": 400,
    "instance": "/orders",
    "code": "validation_failed",
    "errors": { "quantity": [ "Must be between 1 and 100." ] }
  }
  ```

#### `GET /orders/{id}`
Get one order. Reads only order-db; calls no other service.

- **200 OK:** an Order.
- **Errors:**

  | Status | `code` | When |
  |---|---|---|
  | 400 | `validation_failed` | `id` isn't an integer |
  | 404 | `order_not_found` | No order with that ID |
  | 503 | `service_unavailable` | order-db unreachable |
  | 500 | `internal_error` | unexpected error |

#### `GET /orders?userId={id}`
List a user's orders, newest first.

- **200 OK:** `{ "items": [ Order, ... ] }`. If the user has no orders, or doesn't exist, the response is `{ "items": [] }`. The user isn't checked with user-service: filtering a collection by an unknown value simply matches nothing.
- **Errors:**

  | Status | `code` | When |
  |---|---|---|
  | 400 | `validation_failed` | `userId` missing or not an integer |
  | 503 | `service_unavailable` | order-db unreachable |
  | 500 | `internal_error` | unexpected error |

### 5.4 Health endpoints

Every HTTP service (gateway, product-service, user-service, order-service) exposes two endpoints, following the common liveness/readiness split. They are for Docker only and aren't routed through the gateway.

| Endpoint | Checks | Healthy | Unhealthy |
|---|---|---|---|
| `GET /health/live` | Only that the process is running and answering HTTP. **No dependencies.** | `200`, body `Healthy` | (no answer at all) |
| `GET /health/ready` | That the service can do its job: **its own database** is reachable. Never checks other services. | `200`, body `Healthy` | `503`, body `Unhealthy` |

- The gateway and payment-service have no database, so for them ready means the same as live.
- **Why readiness never checks other services:** if order-service reported "not ready" whenever product-service was down, one failing service would mark every service that calls it unhealthy as well. A health check answers "can *I* work?", not "is the whole system working?".
- The bodies are plain text (ASP.NET Core's health-check default) and aren't part of the contract. Only the status code matters.
- Docker's `healthcheck` uses `/health/ready`, so that `depends_on: condition: service_healthy` waits until a service can actually serve requests. The `aspnet` runtime images don't include `curl` or `wget`; how the health check makes the request is decided in step 2.
- payment-service speaks only HTTP/2. Its health check is decided in step 4 (see architecture.md, open question Q1).

## 6. Order-service dependency-failure translation

Each row is one outcome of one call that order-service makes during `POST /orders`. "Couldn't connect" covers connection refused and DNS failure.

| Dependency | Outcome | order-service responds | `code` | Order |
|---|---|---|---|---|
| user-service | 200 | continue | – | – |
| user-service | 404 | 422 | `user_not_found` | not created |
| user-service | other 4xx | 500 | `internal_error` | not created |
| user-service | 5xx | 502 | `dependency_failed` | not created |
| user-service | couldn't connect | 502 | `dependency_failed` | not created |
| user-service | timeout | 504 | `dependency_timeout` | not created |
| product-service | 200 | continue | – | – |
| product-service | 404 | 422 | `product_not_found` | not created |
| product-service | other 4xx | 500 | `internal_error` | not created |
| product-service | 5xx | 502 | `dependency_failed` | not created |
| product-service | couldn't connect | 502 | `dependency_failed` | not created |
| product-service | timeout | 504 | `dependency_timeout` | not created |
| order-db | insert fails (before payment) | 503 | `service_unavailable` | not created |
| payment-service | `OK`, `success = true` | 201 | – | `PAID` |
| payment-service | `OK`, `success = false` | 201 | – | `FAILED` (decline reason) |
| payment-service | `UNAVAILABLE` (couldn't connect) | 502 | `payment_unavailable` | `FAILED` |
| payment-service | `INTERNAL` or any other non-OK status | 502 | `payment_unavailable` | `FAILED` |
| payment-service | `DEADLINE_EXCEEDED` / timeout | 504 | `payment_timeout` | stays `PENDING` |
| order-db | status update fails (after payment) | 503 | `service_unavailable` | stays `PENDING` (see [§8](#8-known-gaps)) |

Why:

- **A 400 from user-service or product-service is order-service's own bug.** Order-service built a bad request, so it isn't the client's fault and isn't the dependency's fault either. It's an internal error.
- **A connection failure to payment-service marks the order `FAILED`.** The request never reached payment-service, so nothing was charged. The same is assumed for `INTERNAL`, since payment-service is a simulation with no side effects.
- **A payment timeout leaves the order `PENDING`.** The request may have reached payment-service and been processed after the caller stopped waiting, so the outcome is unknown and `FAILED` could be a lie.

## 7. Default timeouts in M1

M1 sets no timeouts of its own (decision D5). These are the defaults in effect, from the outside in:

| Hop | Component | Default |
|---|---|---|
| browser → nginx | browser `fetch` | no timeout |
| nginx → gateway | `proxy_connect_timeout` / `proxy_read_timeout` | 60 s / 60 s between two reads |
| gateway → services | `HttpClient.Timeout` | 100 s |
| order-service → user-service, product-service | `HttpClient.Timeout` | 100 s |
| order-service → payment-service | gRPC deadline | **none: waits forever** |
| services → Postgres | Npgsql `Timeout` (connect) / `Command Timeout` | 15 s / 30 s |

Consequences:

- **The outermost timeout is the shortest.** nginx gives up after 60 s, while everything behind it waits up to 100 s. A slow request therefore ends with nginx's own HTML 504 page, which isn't Problem Details and has no `code`. The gateway's `upstream_timeout` never reaches the browser.
- **A hung payment-service hangs order-service indefinitely.** The caller times out, but order-service keeps waiting on the gRPC call and the order stays `PENDING`.
- **A timeout upstream doesn't cancel the work downstream.** When the gateway gives up, order-service carries on unless it observes `HttpContext.RequestAborted`.

These are fine for M1. Failure Exercise 2 (slow payment) will make them very visible.

## 8. Known gaps

Deliberately not solved in M1:

| Gap | Effect | Usual fix |
|---|---|---|
| No idempotency | A client that retries `POST /orders` after a timeout or network error creates a second order and a second payment | `Idempotency-Key` request header: the server stores the first response for each key and replays it |
| Payment timeout leaves `PENDING` forever | Nothing ever resolves orders whose payment outcome is unknown | A reconciliation job that asks payment-service for the real outcome |
| Status update can fail after a successful payment | The customer is charged, but the order stays `PENDING` | Outbox pattern, retries, or reconciliation |
| No coordinated timeouts | Outer layers give up before inner ones, and work continues after nobody is waiting | A timeout budget that shrinks at each hop (deadline propagation), plus cancellation |
| `GET /orders?userId=` isn't paginated | Unbounded result size | Cursor pagination, which the `{ "items": [] }` envelope already allows for |
| Sequential integer IDs | Easy to enumerate other users' orders | Random IDs and authorization |
